01 · 把“画一张图”变成一次可以审查的编译

VizIR 是一个跑在命令行上的可视化编译器，用 Rust 写成。你给它一份语义文档——一种叫 .viz.yaml 的文件，里面写清数据、想看的视图和字段怎么映射——它交回一张 SVG 矢量图，或者一张由这份 SVG 栅格化来的 PNG 位图。

它给需要在代码里稳定出图的人用：在 CI 里给测试报告配图、给文档站批量出图、或者让上游的 agent 把“画一张柱状图”落成一份能被人审查的文件。这三种场景的共同要求只有一条——同一份输入，什么时候编译，出来的图都必须一模一样。

和直接拼 SVG 字符串的绘图库相比，VizIR 把这件事拆成三级中间表示，每一级都能单独校验、落盘和逐字节比对；和把图交给浏览器渲染的方案相比，它不依赖任何运行中的服务，一个二进制就够了。它也有明确的不做什么：不解释自然语言里的作图意图，也不替你挑输出后端——命令行只收文件路径，仓库文档把这两件事划给上游的 create-plot 技能1。

01 · 谁在它上游create-plot 技能把意图变成语义文档、决定用哪个后端；VizIR 只对文档本身负责。所以第 04 节的总览图里，create-plot 画在本仓库边界之外。这一条来自仓库自己的文档，代码里没有它的痕迹——命令行只接受文件路径。

02 · 八件它替你做的事

  • 编译前校验：数据集引用、字段类型、编码映射在编译前就查一遍，报错带错误码和出问题的位置；适合在 CI 里挡住写坏的文档。
  • 一键渲染：vizir render --format svg|png 一条命令出图；适合文档站和 CI 产物。
  • 三类图表方言：统计图（散点 / 折线 / 柱状）、关系图、自由几何，同一份文档可以混着用；适合一页报告里既有柱状图又有流程图。
  • 中间表示落盘：vizir normalize 导出带 JSON Schema 的中间表示，可以 diff、可以喂给别的工具；适合审查“编译器到底理解成了什么”。
  • 分层布局服务：关系图给了坐标就用你的坐标，没给就自动分层排布，成环也有确定的兜底位置；适合不想手摆节点的场景。
  • 溯源查询：vizir explain 回答“图上这个元素从哪来”；适合核对生成结果有没有画错数据。
  • 能力协商与损失清单：渲染前问一遍目标后端能做什么，做不到就报错；PNG 这类有损路径在清单里写明降级了什么；适合在自动化里提前发现出不了图。
  • 场景增量修订：场景以修订号描述差异，可以 diff 与应用；目前只有库接口，命令行还没有入口。

这八条到此为止：读者知道有这个能力、知道谁在什么场景用它就够了，每条能力内部怎么运转属于下一层文档的范围。

04 · 一条编译链，两端各有一道边界

整个系统只有一个进程。图表作者与 create-plot 技能把语义文档交给 vizir 命令行，命令行在本进程里跑完编译链，写出 SVG 与 PNG 制品；只有 PNG 这一条路要走出进程，去调外部的栅格化器。把这一点记住，后面四张图都是这条链的放大。

六个盒子各管一件事。图表作者把数据与视图写成文档；create-plot 技能替作者合成这份文档，也可以直接调子命令；vizir 命令行是本仓库唯一的入口，它读语义文档、在本进程里跑完编译链、写出制品；SVG 与 PNG 制品落在输出目录；栅格化器在进程外，只在目标为 PNG 时被调用。走一遍：作者写好文档 → 命令行读取 → 编译链跑完 → SVG 写盘 → 若目标是 PNG，命令行再调栅格化器把这份 SVG 变成位图并回读校验。

一个容易混的边界：栅格化器画在本仓库之外，因为它是一个外部可执行程序，命令行只是找到它并调用；机器上没有它，PNG 这条路就走不通，SVG 不受影响。图上五条都是实线，所以这张图不画线型图例；灰底的两个盒子（create-plot 技能与栅格化器）不在本仓库里。点击任一盒子会跳到讲它的那一段。按预算删掉的是清单文件与缓存目录——清单在第 07 节的时序里出现，缓存这个仓库根本没有。

05 · 主走查：一次渲染

下面这条链贯穿全系统，后面四张图各是它的一段放大。五个环节各点名它经过的组件与它做的一件事。

  1. 写文档——图表作者（或 create-plot 技能）把数据与视图写进一份语义文档，数据集、视图、字段映射都在这一个文件里。
  2. 校验——vizir 命令行把文档交给 vizir-compiler，第一轮校验在语义层查数据集引用与字段类型，这一步过不去就没有后面。
  3. 降阶与布局——编译器把语义文档降成中间表示：表达式定下类型、标度定下值域；第二轮校验再查一遍，关系图在这一步拿到坐标。
  4. 成场景并协商——场景构建产出 Scene2D，每个节点带上“我从哪来”的出身信息；能力协商逐条判定这些节点报出的需求，有一条不满足就整体失败。
  5. 出制品——SVG 后端逐字节确定地写出 SVG；目标为 PNG 时，命令行再调外部栅格化器把它变成位图并回读校验，清单里记下降级损失。
这条走查的名字在全站通用
「一次渲染」是本页选定的主线名：讲单个能力怎么运转的文档会沿用这个名字来说明自己承担哪一段，换名字会让两层文档对不上。

06 · 编译流水线：三个 crate 各管一段

把命令行那个进程拆开看，是三个 crate 在接力：vizir-core 定契约、做校验与能力协商；vizir-compiler 负责降阶、布局与场景构建；vizir-cli 负责写出制品。下图按“这一步归谁负责”分成三条带，粒子沿主链跑。

三条带就是三个 crate。最上一条是 vizir-core：HIR 校验收下语义文档并查数据集引用与字段类型，MIR 校验在降阶之后再查一遍，能力协商在渲染前逐条判定。中间一条是 vizir-compiler：降阶把 HIR 变成 VizMIR，分层布局给没有坐标的关系图算坐标，场景构建把 MIR 变成 Scene2D。最下一条是 vizir-cli：SVG 输出逐字节写盘，PNG 栅格化调外部栅格化器并回读校验。走一遍主链：HIR 校验 → 降阶到 MIR → MIR 校验 → 分层布局 → 场景构建 → 能力协商 → SVG 输出 → PNG 栅格化。

易混点：能力协商排在场景构建之后，不是之前——判定需要场景节点自己报出的需求（比如要不要透明背景），这些需求要到场景生成时才齐全。图上粒子沿三条主线跑，同周期不同相位；带子只是责任归属，不是运行顺序的框。按预算删掉的是清单写盘与错误退出路径，它们在第 07 节出现。

07 · 渲染时序：谁在等谁

主走查的第三到第五个环节发生在命令行进程里，外面看不见。把它按时间拉开就是下面这张图：四个被调用方都只在被调用的那几步打开，命令行从头活到尾。

五条生命线，一条主动。命令行从第一步活到最后一步，它的激活条贯穿全图；编译器只在第一到第三步被打开，两轮校验它自己不判断，而是请核心契约来判；核心契约是契约层，校验诊断与能力协商的结论都出自它；SVG 后端只收场景、交文本；栅格化器是进程外的可执行程序。走一遍：命令行把文档交给编译器并取回场景 → 编译器请核心契约做两轮校验 → 有诊断就直接终止，后面的步骤都不会发生 → 命令行自己做能力协商 → SVG 后端把场景写成矢量图 → 目标为 PNG 时再调一次栅格化器。

易混点：OPT 框里的第六步只在目标是 PNG 时发生，SVG 目标到第五步就结束了；第四步的箭头从命令行直指核心契约，跳过编译器，因为协商由命令行发起、不需要编译器转手。返回消息用更细的灰线并以“返回”开头，好分清请求与应答。按预算删掉的是清单写盘与栅格化器缺失时的报错分支。

08 · 能力协商：先问能不能，再动手

渲染前有一道闸门。场景节点在生成时报出自己需要什么能力，闸门把它们逐条对照目标后端的能力档案——档案就是一份“我能做什么”的声明。结论只有三种：精确放行、降级放行、整体拒绝。

判定逐条进行，结论只有三种。场景需求是 Scene2D 节点在生成时报出的“我需要什么”，比如二维场景本身、文本、或者透明背景。能力协商把它们逐条对照目标后端的能力档案：SVG 档案原生支持二维场景与文本，所以精确放行，产出 SVG 文本；PNG 档案要把这些需求降级成栅格制品，放行但在清单里记一笔损失；没有档案认领的需求（动画时间线、指针交互、三维网格、纯矢量目标）直接拒绝，整次渲染以错误码收场，一个字节都不产出。把鼠标放到任一盒子上，与它相连的路径会亮出来。

易混点：左下角那个虚线框里的需求目前不会出现——现在的语义文档表达不了动画与三维，所以拒绝分支画成短虚线并带问号，它是给未来留的闸门，不是已经在跑的分支。停止记号用实心墨点而不是主题蓝，表示“这里没有产物”。按预算删掉的是清单里 capability_report 的字段展开，它在页脚的核对信息里出现。

09 · 溯源与稳定身份：两条河，一个汇合点

场景里每个节点都带着一份出身信息：它来自哪一行数据、由哪一步生成。这一份信息分成两条完全不同的河——数据行谱系回答“这个图形对应哪行数据”，生成谱系回答“这个图形是哪一步画出来的”。

两条河，一个汇合点。蓝的一条是数据行谱系：数据集 sales 的每一行先变成带类型的行表达式，再经值标度定出值域，最后落到柱节点上；写出的 SVG 矩形带着 data-lineage 属性，回答“我来自哪一行”。朱红的一条是生成谱系：图框决定画布与绘图区，网格与轴把标度刻成参考线，轴节点（比如 grid/y/0）不来自任何一行数据；它写出的 SVG 直线只记生成步骤。在图例按钮上停留或点击可以只看一条河，按 Escape 恢复两条。

易混点：两条河在 SVG 元素汇合，但身份不同——柱矩形的出身是数据行，轴直线的出身是生成步骤，SVG 里靠不同的属性区分，而不是靠类名。按预算删掉的是文字标签与图例节点，它们同样没有数据谱系，走的是生成谱系这一条。

展开：用一条命令核对图上这两个出身 
$ vizir explain examples/chart/sales-regions.viz.yaml --node revenue-bars/bar/south
data-lineage: data/sales
generated-by: build-bar-scene

$ vizir explain examples/chart/sales-regions.viz.yaml --node revenue-bars/grid/y/0
generated-by: build-guide-scene
（没有 data-lineage 行：轴节点不来自任何一行数据）

三级中间表示，每级可落盘校验和比对可以停在任意一级，坏输入最早在语义层就被挡下同一张图要同时理解文档、中间表示、场景三层名字

PNG 走外部栅格化器不自己实现光栅化，SVG 与 PNG 来自同一条路径机器上没有 rsvg-convert 或 magick 就出不了 PNG

展开：机器上没有栅格化器时会发生什么

命令行按顺序找 rsvg-convert、再找 magick，两个都找不到就不产出 PNG：SVG 已正常写盘，PNG 目标以错误结束。栅格化成功后它还会回读位图，校验文件头是 PNG、像素带透明通道，并且在该图确实需要透明背景时，确认图里同时存在透明与可见像素——防止栅格化器悄悄垫了白底。这段核对信息来自本机重跑，不是转述文档。
